# Gate Observability — Gate and Tracker

DEV-53 adds a small composite action to the existing protected production workflow. Pin it to a reviewed DevOps commit. It runs on the existing coordination runner; it does not rebuild images or call an AI model.

## What a release must prove

1. The checked-out protected main tree equals the exact source tree that produced the candidate images. Gate uses its successful develop-to-main release PR build; Tracker uses the successful image job in its main deployment run.
2. All enrolled runtime groups and physical processes remain listed in `.gate/observability.json`. The action's pinned policy owns the required set. Gate requires PHP, browser and Nitro coverage; Tracker requires API/MCP, all four PHP workers and browser coverage.
3. The new candidate records every exact image digest, release SHA and debug IDs. JavaScript maps were checked/uploaded by the successful build and are absent from public assets. Gate compares private maps from that build with the compiled image; Tracker retains its existing map validation/removal step and collects IDs from the exact nginx image.
4. The SDK dependency closure/initialization, intake routing, privacy filters and relevant build/symbol configuration match a verified chain. Normal application changes can reuse that chain. Relevant changes block until new actual SDK → Sentry → Heal evidence is enrolled.

The `Gate Observability` action fails before application deployment when any required input is absent, stale or inconsistent. Caller workflows must require the job/step and preserve existing security checks. There is no permissive fallback or `continue-on-error`.

## Evidence and trust

The action carries its reviewed policy and sanitized historical chain evidence. Each proof records original verification source, run/attempt, artifact digest, actual Sentry event/issue and Heal-case identifiers, resolved frame, privacy/deduplication counts and zero fix attempts. The policy pins the canonical proof hash. The original short-lived artifact identity is retained; archived evidence does not imply an expired GitHub artifact can still be downloaded.

These records were enrolled from the actual IN-37 and TRAC-202 verification results. See `.github/actions/gate-observability/evidence/`. No DSN, upload key, raw event payload, user content or source-map content belongs in this evidence. Shared intake source used for the fingerprint is a pinned source snapshot without runtime configuration or credentials.

On every release, GitHub's run/attempt metadata independently binds the candidate to the expected workflow, source, repository and successful image job. Policy and historical evidence come from the pinned action, not from a candidate PR. Candidate receipts are generated by that protected workflow after the existing immutable-image/security checks.

Tracker consumes the approved Gate intake snapshot. Gate's own guard also compares its Tracker routing projection with that snapshot. A change to Tracker's intake therefore requires renewed Tracker evidence and a normal reviewed policy update, even when Gate's own route is unchanged. Adding an unrelated route does not change either enrolled projection.

## Integration fingerprints

`computeFingerprints` reads exact Git objects as data. It never runs repository code, package lifecycle hooks or candidate tools. Four SHA-256 fingerprints cover:

- Sentry's resolved Composer/pnpm dependency closure, relevant patches and initialization;
- shared intake implementation plus only this repository's installation/project/component route;
- privacy-filter source;
- relevant Docker/build/symbol files and the selected workflow steps, their matrix and inherited configuration.

An independent guard job or ordinary code edit leaves the fingerprints unchanged. A changed Sentry dependency, init/filter, route or symbol build input requires renewed chain evidence. Explicit selectors are part of the pinned policy; callers cannot shrink them.

## Caller contract

Use `Tuinstra-DEV/devops/.github/actions/gate-observability@<full-reviewed-sha>` with inputs `candidate`, `manifest` (default `.gate/observability.json`) and `output`. The job needs Contents/Actions read plus `GITHUB_TOKEN` for its own repository. The workflow must use a full-history checkout and run on protected main.

The candidate JSON contains `repository`, `source_sha`, `source_tree`, `run` (`workflow`, `id`, `attempt`, `source_sha`), `artifacts` (exact image digests) and `symbols` per JavaScript component (`source_sha`, `artifact_digest`, `uploaded`, `public_maps`, `debug_ids`). The collector only measures compiled files; the protected build establishes upload success. PHP uses original source instead of a symbol bundle. Collection excludes bundled `node_modules`; required first-party map coverage is checked against nonempty mapped source and the enrolled live frame. Generated helper chunks without maps are listed separately as `unmapped_debug_ids`, never presented as symbolicated. The collector compares the complete debug-ID set with the compiled image.

For image-archive collection in the same job, invoke the pinned action with `prepare-only: true`, then use its `collector-script` output to derive symbols and invoke its `run-script` output with the candidate, manifest and output environment variables. Preparation alone is never a successful release gate. The caller must run validation before its promotion loop.

The action returns a sanitized assurance receipt. Keep it with the existing deployment evidence and verify the actual running images/configuration against it after deployment. Retain the previous exact images, database version, compose configuration and prior assurance receipt before updating the rollback pointer.

## Rollback and emergencies

A rollback reuses the previous verified image digests, configuration and assurance receipt. Do not replace an image under its recorded digest or silently reuse proof for another source. Keep existing database safeguards and operator-owned receipts.

No automatic emergency bypass is implemented. A deliberate exception requires a recorded human decision with reason and exact version, followed through the existing recovery procedure. A missing proof cannot become green through an environment flag.

## Local checks

Run the focused Node tests, then `make lint` and `make test`. The latter uses the existing documented Ansible prerequisite. Tests use synthetic candidate/symbol data; historical technical records are labeled separately. Deployment green/negative proofs and active-runtime checks remain delivery gates for DEV-53.
